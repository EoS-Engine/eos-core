## Objective
Create the full solution skeleton (`EOS.slnx`) with all 33 Part 1 §1.1 projects, correctly wired per Part 1 §1.2's dependency table, so the R-00 (no circular references) fitness rule is meaningfully testable. No business logic, no DTOs, no bootstrap logic.

## Scope

**Included:**
- Physical layout: `src/`, `tests/` (existing `docs/` untouched). `benchmarks/`, `config/`, `scripts/`, `deploy/`, `prompts/` are **not** created yet — nothing in WP-001 requires them; they are created by the WP that first needs their contents (config/ → WP-002, etc.), per YAGNI.
- All 33 Part 1 §1.1 projects, empty (no `.cs` files beyond what's listed below), wired with `ProjectReference`s matching Part 1 §1.2 exactly.
- `EOS.SharedKernel`: `Entity<TId>`, `EntityId`, `ValueObject` — the only source files in WP-001, because the Roadmap names these specifically as WP-001's deliverable and they are immediately usable primitives, not speculative DTOs.
- `EOS.Core`: empty (no cross-cutting kernel type is yet needed by anything in WP-001; the project exists as the registered leaf dependency target).
- `tests/EOS.ArchitectureTests`: one xUnit test parsing every `.csproj`'s `ProjectReference` elements and asserting the resulting graph has no cycle (topological sort succeeds). No third-party architecture-testing library — a plain graph walk is simpler and sufficient for this one rule.
- `EOS.Mobile`: real `flutter create` scaffold, zero `.csproj`/`.dll` references (R-07).
- `EOS.Runner`: empty console app, **zero project references**. Part 1 §1.2 lists it as depending on "everything," but that describes its role once composition actually exists (WP-002 onward); wiring 32 references today with nothing to compose would be a God Project with no purpose. References are added incrementally, WP by WP, only when a project is actually composed into the host.

**Explicitly excluded / deviations from the original WP-001 field, and why:**
- **`EOS.Contracts` interface shapes** — the Roadmap's WP-001 row names these, but every one of the 9 interfaces (`IKnowledgeClient`, `IReasoningEngineClient`, etc.) needs request/response types that don't exist yet. Writing the interfaces now would force placeholder/fake DTOs, which is explicitly disallowed. `EOS.Contracts` is scaffolded empty; each interface is added by the WP that also defines its real DTOs (e.g. `IAIProviderClient` arrives with WP-005, alongside a real `InferenceResult`). This is a deliberate, flagged deviation from the WP-001 row's literal wording, not a silent one — it does not violate the Roadmap's dependency ordering (nothing in WP-002–WP-004 consumes any Contracts interface) and is fully reversible.
- Any business logic, any role project's behavior.
- Any data store connection (WP-004), any event/`EventEnvelope` mechanism (WP-003), Bootstrap sequence or config schemas (WP-002).

## Acceptance Criteria
- `dotnet restore` succeeds.
- `dotnet build` succeeds — zero errors, zero warnings.
- `dotnet test` succeeds (architecture test passes).
- `dotnet format` succeeds with no changes required.
- No placeholder code, no TODOs, no dead code anywhere in the diff.
- `flutter analyze` (or `flutter create` succeeding) confirms `EOS.Mobile` builds independently with no `.NET` reference.
- Repository remains clean (nothing untracked left behind, `.gitignore` covers all build output).

## Risks
- **Contracts deviation** (above) — flagged, reversible, does not block any later WP since none of WP-002–004 need a Contracts interface.
- **Flutter first-time install** — scoped strictly to enabling the `EOS.Mobile` scaffold; no other project depends on it.
- **`.slnx` vs `.sln`** — `.slnx` is the current .NET 10 default and functionally equivalent; all commands in this plan use `EOS.slnx` explicitly.

## Definition of Done
`dotnet restore/build/test/format` all succeed; zero warnings; zero placeholder/TODO/dead code; all 33 projects exist and compile; dependency graph matches Part 1 §1.2 with no cycles; repository clean; one commit.
