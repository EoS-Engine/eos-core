# ADR-001 — WP-015 Embedding Generation Reachability

> **Superseded by `ADR-015-001-Embedding-Generation-Reachability.md`** (Status: Accepted). This document is preserved unmodified as the historical Proposed-stage analysis.

## Status

Proposed

## Context

WP-015 must implement `consolidate()` (Memory-Management-Specification-v1.0 §16.2), which requires `EOS.Knowledge` to invoke embedding generation. `EOS.Knowledge`'s Constitution-declared dependency shape does not grant a path to the project where that capability lives. This recurs a gap first identified during WP-014's Architecture Review (Gap 1), which WP-014 ultimately avoided because it had no real caller for the capability; WP-015 cannot avoid it, since `consolidate()` is the specified algorithm this WP must deliver.

## Problem Statement

How is `EOS.Knowledge` architecturally permitted to invoke `EmbeddingProvider.embed(...)` given its current dependency shape?

## Evidence

`EOS-Specification.md` Part 1 §1.2:
> "| EOS.Knowledge | Principal Engineer | EOS.KnowledgeGraph, EOS.VectorStore | Role projects |"

`EOS-Specification.md` Part 1 §1.2:
> "| EOS.AIProvider | AI Architect (policy), Principal Engineer (impl) | EOS.Contracts, EOS.SDK | A third consumer channel beyond EOS.Reasoning (`infer`) and EOS.Knowledge (`embed`) |"

`EOS-Specification.md` Part 1 §1.2:
> "| EOS.Learning | Principal Engineer | EOS.Contracts, EOS.Knowledge, EOS.SDK | Role projects (no role project depends on it directly) |"

Memory-Management-Specification-v1.0 §16.2:
> "embedding = EmbeddingProvider.embed(episodic_entry.content)    # delegated, §14"

Memory-Management-Specification-v1.0 §14:
> "Every unit of content entering Episodic, Semantic, or Long-term Memory is assigned an embedding at consolidation time (§16), generated by invoking an AI Provider's embedding model (Constitution §0.14) through a defined client interface (`IEmbeddingProviderClient`, §20) — Memory owns *when* to index, never *how* the embedding model computes the vector (FR-M3)."

## Considered Options

**Option A — Amend Constitution Part 1 §1.2** to add `EOS.SDK` to `EOS.Knowledge`'s "Depends On" column.

**Option B — Composition Root Adapter Pattern.** `EOS.Knowledge` defines a small, BCL-typed interface (e.g., `Task<IReadOnlyList<float>> EmbedAsync(string content, CancellationToken)`); `EOS.Runner`'s `Program.cs` supplies the concrete adapter, internally invoking `AIProviderManager`. Matches the already-merged `IProviderEventLogger`/`LoggerProviderEventLogger` pattern (WP-010/011).

**Option C — Route the embed call through `EOS.Reasoning`** (which already has `EOS.SDK` access).

## Pros / Cons

| Option | Pros | Cons |
|---|---|---|
| A | Resolves the Constitution's own internal inconsistency permanently; simplest code (direct reference); high future extensibility. | Requires out-of-band Constitutional-amendment governance (§0.6: Constitutional amendment requires CTO + Principal Engineer consensus, human sign-off) before any code is written. |
| B | Zero Constitution edit; zero new `ProjectReference`; reuses an already-proven, already-merged pattern; has a genuine caller this time (unlike WP-014's removed attempt). | Recurring small adapter needed for every future similar reachability need — a minor, repeating tax rather than a one-time fix. |
| C | No new pattern needed. | Directly contradicted by Memory-Management-Specification §4, which assigns "invoking (not owning) embedding generation" to Memory itself, not Reasoning; also requires a new `EOS.Reasoning`↔`EOS.Knowledge` coupling not evidenced anywhere. |

## Consequences

Choosing B leaves Constitution Part 1 §1.2's internal inconsistency (the `EOS.AIProvider` row presupposing an edge the `EOS.Knowledge` row doesn't grant) permanently undocumented at the table level — every future WP needing the same reachability will re-apply the same adapter, an accumulating (but bounded, low-cost) documentation debt. Choosing A resolves the inconsistency once, at the cost of a Constitutional-amendment process.

## Recommendation

**Option B.**

## Open Questions

- Should Constitution Part 1 §1.2's inconsistency ever be corrected directly (Option A), independent of WP-015, as a standalone governance action?

## Decision Required

This is a **Cross-cutting architecture** decision per Constitution §0.6's Decision Matrix ("Cross-cutting architecture | Autonomous Decider: Principal Engineer | Consensus Required: CTO"). Requires ratification by the Architecture Board (acting in the Principal Engineer/CTO capacity) before implementation.
